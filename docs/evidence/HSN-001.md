### Erratum — physical bumper wording

The preceding “LB primary click” phrase is retained verbatim as historical
field-evaluation wording. It does not identify the physical control
unambiguously enough to satisfy HSN-001 v2. The approved contract is RB =
primary/left click and LB = secondary/right click. Only physical-click and
cross-repository mapping-compatibility proof are invalidated; lifecycle,
launch, reconnect, performance, blur, and presentation evidence remain valid
at their exact recorded revisions.

The session-timing trace needs one clarification. The first post-check service
snapshot was taken before the owner invoked Return to Gaming Mode, so active
niri and shell units were expected and do not show simultaneous visible
Gaming/Desktop sessions. A later poll overlapped the owner's actual return
action: the shell units stopped first, and final inspection showed Gamescope on
`tty1` with niri, companion, and UI all `inactive/dead`. No teardown defect is
claimed from that sequence.

The evaluation produced two presentation findings while leaving the explicit
owner verdict `pending`:

1. The mouse hover/press implementation draws a competing hover surface, an
   uncontained expanding ripple, and—in cards and the Grid/List selector—up to
   three visually distinct state shapes. This is a **blocking HSN-001 candidate
   repair** under the existing frozen morph/press/state-layer requirements; it
   does not require a contract amendment. The confirmed repair direction is
   one canonical controller/keyboard/pointer selection, immediate pointer-hover
   retargeting through the native sliding/morphing selection surface, and at
   most one additional clipped ripple/press deformation shared by mouse,
   keyboard, and controller activation.
2. The four-pixel right-edge hover anchor is too easy to trigger. The owner
   confirmed this is **nonblocking for HSN-001** and belongs to the future
   hearthOS System Bar outcome. When the App Menu button and Bar placement are
   known, pointer activation should use a generous click target around the
   visible button rather than an invisible hover edge.

The owner selected separate verdicts: HSN-001 will be audited independently on
the corrected signed candidate produced at the HSN-002 delivery stage; HSN-002
does not become accepted merely because that same image satisfies HSN-001.

## Known blockers and limitations

- The owner locally authorized the exact RC.1 rebase and booted the recorded
  signed OCI. This removes the former authorization blocker but does not make
  RC.1 audit-ready.
- RC.1 packaged the QML plugin incompletely, so the installed UI did not start
  reliably during the Gaming Mode to hearthOS Desktop transition. Manual session entry
  could render the launcher, but automatic shell startup failed.
- Controller and keyboard navigation worked and Return to Gaming Mode
  succeeded. Pointer interaction failed. The launcher used oversized spacing,
  poor centering, symbolic placeholders instead of application icons, a heavy
  selected border, and an over-dark scrim that also dimmed the panel.
- In RC.1, Firefox and Dolphin did not remain running. The transient service reported a
  false success while `gtk-launch` descendants escaped the default main-process
  lifecycle, so application survival is not proved.
- RC.1 was visibly laggy and no warmed p95/p99 motion evidence was captured.
  Grid/List persistence, shell-restart survival, receiver reconnect, invalid
  configuration fallback, KDE/TTY recovery, and previous-deployment recovery
  remain untested.
- The gray desktop before manual UI recovery showed that no wallpaper surface
  exists yet. Wallpaper remains outside frozen HSN-001 and is tracked as the
  independent HWP-001 successor work.
- The Fedora workflow RPM and Hearth-local RPM were built from the same clean
  source but are not byte-identical. The sole release identity is the GitHub
  asset SHA-256 below; no bit-for-bit reproducibility claim is made.
- Historical HS-003 tests are salvage inputs only and do not prove this
  contract.
- The owner authorized RC.2 promotion and deployment, but has not recorded an
  HSN-001 acceptance verdict. The signed package and feature image therefore
  exist without implying audit-readiness or acceptance.
- The booted RC.2 image leaves a gray frosted drawer-sized surface visible
  while the launcher is closed. The local two-repository correction passes its
  warm workload, but is intentionally unpublished and uninstalled pending an
  explicit future owner delivery greenlight.
- The booted RC.2 pointer path still contains the competing hover/press
  surfaces and uncontained ripple that failed owner presentation review. The
  clean local repair passes automated and real-niri engineering gates, but its
  live motion has no explicit owner verdict. The independently authorized RC.3
  candidate must package this repair and pass signed-image owner audit.
